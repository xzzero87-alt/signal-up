# PRD — UI 전문가 소집 체계 (UI Collaboration Infrastructure)

**버전** v0.1 · **작성일** 2026-06-02 · **상태** 확정 (검토 후)
**관련 문서** [`../ui-redesign-spec.md`](../ui-redesign-spec.md) (M18 디자인 명세) · [`../../PRD.md`](../../PRD.md) · [`../adr/README.md`](../adr/README.md)

> 이 문서는 "무엇을 그릴지"(= ui-redesign-spec.md)가 아니라, **UI 작업자(사람·에이전트)를 반복 소집할 때의 협업 인프라**를 다룬다.

---

## 1. 배경 / 문제

UI 작업을 할 때마다 (1) 활성 코드베이스가 어디인지, (2) 색상 토큰·클래스 규칙이 뭔지, (3) `settings.js`가 의존하는 불변 속성이 뭔지를 매번 다시 파악해야 한다. 실제로 2026-06-02 세션에서 활성 폴더 판별과 "이미 구현돼 있던 아코디언"을 모른 채 중복 CSS를 추가하는 사고가 있었다.

UI 에이전트/전문가를 부를 때 **컨텍스트 재설명 비용**과 **기존 작업과의 충돌 위험**이 반복된다. 핵심 문제는 UI 작업에 필요한 지식이 코드 곳곳에 암묵적으로 흩어져 있어, 사람이든 에이전트든 매번 "처음부터" 파악한다는 점이다.

## 2. 목표

- UI 작업자가 **한 진입점**만 읽으면 즉시 작업 가능 (재질문 0회)
- 디자인 결정을 **단일 소스(토큰·규칙)**로 고정해 표류(drift)·중복 방지
- 변경 후 **시각적 깨짐을 자동 검증**하는 경로 확보

## 3. 비목표 (Non-Goals)

- 디자인 자체의 전면 개편 (차콜+블루 테마는 확정으로 간주)
- 자동매매·도메인 로직 ([ADR-0002](../adr/0002-no-autotrading.md) 불변)
- 외부 SaaS 호스팅형 디자인 툴 도입 ([ADR-0006](../adr/0006-self-hosted-distribution.md))
- 프론트엔드 프레임워크 교체 (Vanilla JS + Jinja2 유지)

## 4. 요구사항

### R1. UI 진입점 문서 — `docs/ui/README.md`

UI 에이전트가 가장 먼저 읽는 단일 파일. 포함:

- 활성 코드베이스 경로와 파일 맵 (`templates/`, `static/css/app.css`, `static/js/`)
- **변경 금지 / 주의 영역** — 특히 `settings.js` 의존 속성(`id` / `name` / `data-field` / `err-{field}`)은 디자인을 바꿔도 보존
- 인라인 `<script>` vs 외부 `js` 배치 규칙
- 페이지 목록과 각 페이지 담당 템플릿/API 매핑

### R2. 디자인 토큰 단일 소스 + 문서화

- `app.css`의 `:root` 토큰이 유일한 색상·간격·radius 출처임을 명문화
- 토큰표 문서: 토큰명 / 다크값 / 라이트값 / 용도 / 사용처
- 하드코딩 색상(`#xxxxxx`, 인라인 `rgba(...)`) 금지 규칙 — CSS 스캐너로 위반 검출

### R3. 컴포넌트·패턴 카탈로그 (라이브 스타일가이드)

- 내부 라우트 `/_styleguide` (운영 빌드에서는 노출 제어)
- 실제 토큰을 끌어다 버튼·칩·아코디언·스텝퍼·테이블·배지(매수/매도/강도)를 한 페이지에 렌더
- 다크/라이트 토글 포함 → 신규 컴포넌트의 일관성 비교 기준

### R4. 시각 회귀 검증 경로

- 변경 후 최단 검증: Jinja2 렌더 테스트 + (선택) 헤드리스 스크린샷 비교
- **CSS 클래스 ↔ 템플릿 클래스 매칭 점검** 스크립트 (2026-06-02 수동 점검을 재사용 가능하게)
- **중복 CSS 정의 검출** — 한 클래스가 2회 이상 정의되면 경고

### R5. UI 에이전트 역할 정의 (소집 템플릿)

- UI 작업 분할 표준 역할: 탐색 / 토큰·CSS / 템플릿·구조 / 접근성 / 검증
- 각 역할의 입력·산출·금지 영역을 정의해, 호출 시 프롬프트로 재사용
- **파일 충돌 규칙**: 같은 파일(`app.css`) 동시 편집 금지. 색상 vs 구조처럼 파일이 겹치지 않는 작업만 병렬화

### R6. (선택) 접근성·반응형 기준

- 대비비(WCAG AA), 포커스 표시(`:focus-visible`), `prefers-reduced-motion`(일부 적용됨)을 체크리스트화
- 사이드바·테이블의 좁은 화면 동작 기준

## 5. 성공 지표

- UI 에이전트가 진입점 1개만 읽고 작업 착수 (재질문 0회)
- 디자인 토큰 외 하드코딩 색상 0건 유지
- UI 변경마다 검증 스크립트 통과 후 머지
- "이미 구현된 것 모르고 중복 작성" 재발 0건

## 6. 단계 (Phasing)

| Phase | 항목 | 비고 |
|-------|------|------|
| **1 (즉시)** | R1 진입점 문서 + R2 토큰표 + R4 검증 스크립트 | 2026-06-02 세션 자산 재활용 |
| **2** | R3 스타일가이드 페이지 + R5 에이전트 역할 템플릿 | |
| **3 (선택)** | R6 접근성·반응형 + 스크린샷 회귀 | |

## 7. 미해결 질문 → 추천안 (확정)

### Q1. 진입점 문서 위치 — `docs/` 아래 vs CLAUDE.md 링크?
**추천: `docs/ui/README.md`에 본문을 두고, 두 `CLAUDE.md`의 "진입점 문서" 목록에 한 줄 링크만 추가.**
근거: 기존 진입점(PRD·DESIGN·runbook)이 모두 파일이고 CLAUDE.md는 "인덱스" 역할이라는 프로젝트 관례와 일치. 본문을 CLAUDE.md에 넣으면 비대해지고, 코드 진입 시 매번 로드되는 비용이 커진다.

### Q2. 스타일가이드 — 라이브 라우트 vs 정적 HTML?
**추천: 라이브 내부 라우트 `/_styleguide` (Jinja2 + 실제 `app.css` 로드).**
근거: 정적 HTML은 토큰이 바뀌면 또 표류한다. 실제 CSS를 그대로 끌어다 쓰는 라이브 페이지여야 "단일 소스" 원칙이 유지된다. 웹 바인드 기본값이 `127.0.0.1`(로컬 전용)이라 노출 위험도 낮다. 단, 운영 빌드에서는 환경변수/디버그 플래그로 노출 제어.

### Q3. 검증 — CI 게이트 강제 vs 수동?
**추천: 단계적. Phase 1은 수동 스크립트(`scripts/ui_check.py`)로 시작, 안정화 후 기존 품질 게이트(ruff/mypy/pytest 옆)에 합류.**
근거: 검증 로직(클래스 매칭·중복 검출)이 아직 미성숙해 곧바로 CI에 넣으면 오탐으로 머지가 막힐 수 있다. 수동으로 1~2 사이클 돌려 신뢰도를 쌓은 뒤 게이트화하는 것이 안전하다.

## 8. 다음 작업 (Phase 1 착수 시)

1. `docs/ui/README.md` 작성 → 두 `CLAUDE.md` 진입점 목록에 링크 추가
2. `app.css` 토큰표를 `docs/ui/README.md` 내 또는 별도 `tokens.md`로 추출
3. `scripts/ui_check.py` — (a) 템플릿이 쓰는 클래스가 CSS에 존재하는지, (b) CSS 클래스 중복 정의, (c) 하드코딩 색상 검출
